# Теория: моделирование бизнес-процессов в нотации BPMN 2.0

## Цель модуля

Научиться визуализировать и анализировать бизнес-процессы «As Is» («Как есть») и проектировать «To Be» («Как будет»).

## 1. Нотация BPMN 2.0

BPMN (Business Process Model and Notation) — стандарт графического описания бизнес-процессов. Диаграмма одинаково читается аналитиками, разработчиками и бизнесом. Главные принципы:

- процесс читается слева направо;
- одна задача описывает одно действие, название по схеме «глагол + объект» («Подготовить оффер»);
- у каждого процесса есть начало и хотя бы одно завершение;
- у каждой развилки подписаны все исходящие ветки («Да» / «Нет»).

## 2. Основные элементы

### Пул (Pool) и дорожка (Lane)

- **Пул** — участник процесса (компания, организация).
- **Дорожка** — роль или подразделение внутри пула (Рекрутер, Технический лид, HR-отдел). Показывает, кто отвечает за шаг.
- Взаимодействие между разными пулами показывают пунктирными потоками сообщений.

### События (Events)

| Тип | Обозначение | Назначение |
|---|---|---|
| Start (начальное) | тонкий круг | процесс начинается |
| Intermediate (промежуточное) | круг с двойной линией | что-то происходит по ходу процесса: сообщение, таймер |
| End (конечное) | толстый круг | процесс завершается, подписывается результатом |

Пример: **граничное событие-таймер** на задаче «Согласовать оффер» («24 часа») запускает напоминание, если согласование затянулось.

### Задачи (Tasks)

| Тип | Что значит |
|---|---|
| Task | действие без уточнения типа |
| User Task | действие выполняет человек в системе |
| Service Task | действие выполняет система автоматически (значок шестерёнки) |

В диаграмме «To Be» Service Task показывает, какие шаги автоматизированы.

### Шлюзы (Gateways)

| Шлюз | Знак | Логика |
|---|---|---|
| Exclusive (XOR) | X | выбирается одна ветка по условию («Кандидат подходит?») |
| Parallel (AND) | + | запускаются все ветки одновременно, затем сходятся |
| Inclusive (OR) | O | выбирается одна или несколько веток по условию |

Правило: параллельный шлюз, который делит процесс, нужно закрывать параллельным шлюзом, который собирает ветки обратно.

## 3. Анализ «As Is»

«As Is» — описание процесса в том виде, в котором он работает сейчас. Задача анализа — найти **узкие места**:

- ручные и повторяющиеся операции;
- ожидания и простои между участниками;
- последовательные шаги, которые можно выполнять параллельно;
- шаги без регламента сроков;
- потери и дублирование данных.

## 4. Проектирование «To Be»

«To Be» — целевой процесс после оптимизации. Типовые приёмы:

1. **Автоматизация** ручных шагов (Service Task) с помощью информационной системы, например HRM.
2. **Распараллеливание** независимых шагов (Parallel Gateway).
3. **Контроль сроков** через таймеры и автоматические напоминания.
4. **Единый источник данных** вместо переписки и таблиц.
5. **Сокращение передач** между участниками.

Результат «To Be» должен быть измеримо лучше «As Is»: меньше ручных шагов, короче цикл, меньше потерь.
